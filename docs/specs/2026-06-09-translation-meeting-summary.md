## 1. 项目概述

### 背景
用户团队（中国人，中文/英文为主）与日本客户进行产品演讲会议，需要实时双语翻译并自动生成会议纪要。现有的 `translation.html` 工具支持双语实时翻译，但缺少以下功能：
- 清晰的发言人身份识别
- 会议记录的结构化纪要
- 发言统计和后续行动追踪

### 目标
改造现有翻译工具，增加：
1. **发言人标记** — 用户一键标记"我说"/"对方说"，系统自动关联转录
2. **纪要自动生成** — 会议结束后，AI 自动生成议题、客户反馈、行动项的结构化纪要
3. **可编辑 Word 导出** — 生成可编辑的 DOCX 文件，用户可下载修改

### 使用场景
- **用户身份**: 中国团队（AI 产品方）vs 日本客户
- **会议时长**: 30 分钟 - 1 小时
- **频率**: 每周数次客户会议
- **核心痛点**: 需要快速记录客户反馈和下一步行动

## 2. 功能设计

### 2.1 发言人标记（前端）

**UI 改动**:
- 改造现有 Voice Tab 底部的"甲""乙"按钮
- 新的外观: `🟢 我说` / `🔵 对方说`（彩色标签，易于区分）
- 按钮行为：点击后高亮，表示"接下来的转录属于这个发言人"

**数据流**:
```
用户点"我说" 
  ↓
设置 state.currentMarker = "我说"
  ↓
Deepgram 转录来临
  ↓
自动标记为 marker: "我说"，添加到历史记录
  ↓
显示时用颜色标签区分
```

**转录历史显示**:
- 每条转录前显示发言人标签
- "我说"用绿色，"对方说"用蓝色
- 便于用户实时校验谁说了什么

**数据结构改动**:
```javascript
// 原有结构
{
  speaker: "甲",
  zh: "产品支持实时处理",
  ja: "製品はリアルタイム処理に対応しています",
  timestamp: 1718001234
}

// 新增字段
{
  speaker: "甲",
  marker: "我说",  // 新增：用户的发言人标记
  zh: "产品支持实时处理",
  ja: "製品はリアルタイム処理に対応しています",
  timestamp: 1718001234
}
```

### 2.2 纪要自动生成（后端）

**触发方式**:
- 前端新增"生成纪要"按钮（会议结束后点击）
- 点击前显示确认对话："生成纪要后，当前转录将被保存。确定继续？"

**后端接口**:
```
POST /.netlify/functions/summary
请求体：{
  "dialogues": [
    {
      "marker": "我说",
      "zh": "我们的产品可以实时处理数据",
      "ja": "当社の製品はリアルタイムでデータを処理できます"
    },
    {
      "marker": "对方说",
      "zh": "这个功能很吸引人，成本怎样？",
      "ja": "この機能は魅力的ですね。コストはいくらですか？"
    },
    ...
  ]
}

返回体：{
  "topics": ["产品功能介绍", "定价模型讨论", "实施时间表"],
  "feedback": ["对实时处理能力感兴趣", "对成本有顾虑"],
  "actions": [
    {
      "actor": "我们",
      "task": "准备详细的定价表和 Demo 版本",
      "deadline": "3 天内"
    },
    {
      "actor": "客户",
      "task": "内部评审并反馈初步意见",
      "deadline": "1 周内"
    }
  ]
}
```

**Prompt 设计**（后端 Qwen 调用）:
```
系统角色：你是会议纪要专家，擅长从双语对话（中文和日文）中提取关键信息。

任务：分析以下中日双语对话，生成结构化的会议纪要。

输入对话：
[完整的双语对话]

请按以下格式输出 JSON（不要代码块，直接输出）：
{
  "topics": [...],           // 列表：识别的主要议题（3-5 个）
  "feedback": [...],         // 列表：客户的反馈和顾虑（3-5 条）
  "actions": [...]           // 列表：行动项，包含谁、做什么、到什么时间
}

要求：
- topics：从对话中归纳主要讨论主题，用简洁的名词短语
- feedback：提取客户明确表达的兴趣点、问题、顾虑
- actions：识别对话中双方的承诺或计划（谁做什么到什么时间）
  - 如果没有明确的时间，可写"待定"
  - 优先提取客户的行动，其次是我们的行动
- 禁止编造、推断或猜测。只提取对话中明确说出的内容
```

**成本和性能**:
- 输入 token：一个 1 小时会议 ≈ 5000-10000 字 ≈ 3000-5000 tokens
- 输出 token：纪要 JSON ≈ 500 tokens
- 总成本：¥0.3-0.5 / 次（Qwen-Plus 定价）
- 生成延迟：30-60 秒（用户可接受）

**错误处理**:
- 纪要生成失败：显示错误信息 + "重试"按钮
- 网络超时：使用 `AbortSignal.timeout(30000)`，超时后提示重试
- 格式错误：如果返回的 JSON 格式不对，显示"纪要格式错误，请手动整理"

### 2.3 DOCX 文件生成（后端）

**文件格式**:
使用 Node.js `docx` 库生成 Word 文档（.docx）。

**文档结构**:
```
会议纪要
═══════════════════

日期：2026-06-09
时长：1 小时
参与者：中国团队、日本客户

【议题】
• 产品功能介绍
• 定价模型讨论
• 实施时间表

【客户反馈】
• 对实时处理能力感兴趣
• 对成本有顾虑
• 希望了解数据安全保证

【行动项】
我们：
  □ 准备详细的定价表（3 天内）
  □ 提供 Demo 版本（5 天内）

客户：
  □ 内部评审（1 周内）
  □ 反馈初步意见（2 周内）
```

**实现方式**:
1. 后端接收纪要 JSON
2. 使用 `docx` 库（或 `python-docx` 如果迁移到 Python）生成文档
3. 文档保存在临时目录
4. 返回下载链接给前端

**前端显示**:
- 纪要生成完成后，显示"下载纪要（Word）"按钮
- 点击直接下载 .docx 文件
- 用户在本地 Word 编辑和分发

## 4. 数据流和架构

### 会议全流程

```
初始化
  ↓
用户点"我说" → state.currentMarker = "我说"
  ↓
用户说话 → Deepgram 转录 → Qwen 翻译
  ↓
转录+翻译来临 → 自动标记 marker: "我说" → 显示历史
  ↓
用户点"对方说" → state.currentMarker = "对方说"
  ↓
... 重复多次 ...
  ↓
会议结束 → 点"生成纪要"按钮
  ↓
前端：收集所有转录（含 marker） → POST /functions/summary
  ↓
后端：Qwen 分析 → 生成纪要 JSON → 生成 DOCX → 返回下载链接
  ↓
前端：显示"下载纪要"按钮
  ↓
用户下载 .docx 文件 → 在 Word 编辑 → 分享
```

### 系统边界

| 模块 | 责任 | 使用的外部服务 |
|------|------|---|
| 前端 | 发言人标记、UI、用户交互 | Deepgram（转录）、Qwen（翻译） |
| 后端 | 纪要生成、DOCX 格式化 | Qwen（纪要 AI 分析） |

## 6. 风险和缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Qwen 纪要生成不准确 | 中 | 纪要需要手动修改 | 生成后显示"仅供参考"提示；用户可编辑导出 |
| DOCX 生成库不兼容 | 低 | 文件无法打开或格式错乱 | 提前测试 `docx` 库；预留 HTML/PDF 导出方案 |
| 会议中途网络断联 | 低 | 部分转录丢失 | 保留现有的草稿恢复机制 |
| 发言人标记漏标 | 中 | 纪要中某些发言人身份不清 | 提供"编辑纪要中的发言人标签"的功能（可在 Word 中做） |
